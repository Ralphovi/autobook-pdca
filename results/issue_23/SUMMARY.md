# Security review — issue 23 / normaliser-profiles-version

Attacker-reachable inputs this diff touches: **statement memo text** (threat model, "Where untrusted input enters" #1, written by any counterparty), which reaches `Normaliser.normalise` at `src/autobook/pipeline/normaliser.py:105-117`. The other inputs (profile files and `accounts.toml` in `$XDG_CONFIG_HOME`) are the user's own config, which the threat model lists as trusted.

No findings. What I checked:

- **Crash or hang from a statement memo.** Every shipped pattern was run against hostile 60k–200k character memos: repeated glued tags `EREF+EREF+…`, long punctuation and digit runs that end in a letter (to force regex backtracking), `NR. ` repeated, and 200k spaces. Each finished in under 0.03 s with the `sepa` profile (which also runs every `default` rule). The lazy `.*?` in `src/autobook/pipeline/profiles/sepa.toml` rule 1 always ends at the next tag or `\Z` (end of text). Rules 8 and 9 in `default.toml` can only start a match at a word or whitespace boundary, so they cannot backtrack badly. No ReDoS (a regex that takes runaway time on crafted input). A non-string memo or a bad account tuple raises `NormaliserError`, and the message carries neither value (`normaliser.py:378-390`).
- **Memo text forging a review row.** `" ".join(text.split())` (`normaliser.py:114`) splits on every Unicode line break (`\n`, `\r`, `\x1c-\x1f`, `\x85`, ` `, ` `), so a token cannot hold a line break. Other control characters do pass through: a synthetic memo `SHOP\x1b[2J‮EVIL\nROW\x00` gives the token `SHOP\x1b[2J‮EVIL ROW\x00`. Nothing in this diff writes a token to the review file, a log or a terminal, so this is not a finding here. The future review-file writer has to deal with it, and it shows the raw memo anyway.
- **Personal data reaching a log.** `NormalisedMemo` hides both `raw_memo` and `token` from `repr` (`normaliser.py:76-77`), and a test covers it (`tests/test_normaliser.py:595`). Error messages leave out regex patterns (`:266`) and number account-mapping entries instead of naming them (`:300`). `re.error` and `TOMLDecodeError` messages give a position, not the content.
- **IBAN reaching the model adapter.** A tagged `IBAN+`/`DEBT+` value is dropped up to the next tag. An IBAN has no `+`, so the glued-tag lookahead cannot cut it short and leave part of it behind. An IBAN typed into free `SVWZ+` text survives. The brief puts this out of scope on purpose (brief §Scope and "Strip IBAN-shaped text anywhere. Rejected"), and the adapter boundary is where remote-backend privacy is enforced. Not raised.
- **Making a novel merchant look familiar (abstention erosion).** Tags are found mid-word by design (the brief asks for glued exports to work), so a purpose text like `…ARABIC+…` loses everything after `BIC+`. Only the counterparty can trigger this, and they already control the whole memo, so it gives them nothing new. At worst the token is poor, which the threat model rates Low and which falls through to review. No finding.
- **Version integrity.** `_version` (`normaliser.py:350-372`) hashes every effective rule, the account mapping, `NORMALISER_VERSION` and `unicodedata.unidata_version`. It contains no file paths, so a profile change cannot keep an old version string. Account paths go into the hash only, never in clear text.
- **Pipeline imports.** No `gnucash` import. Only standard-library modules are added.
- **Money, book writes, idempotency, paperless, review-file parsing.** Not touched by this diff.

The T2 gate reported "no security-relevant path touched". That fits: the diff adds no new exposure that would require a threat-model update.
