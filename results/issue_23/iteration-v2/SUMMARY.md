## Findings

- NEEDS-HUMAN [impl] — `src/autobook/pipeline/normaliser.py:148-149`: if the user directory is a **broken symlink**, the loader silently treats it as missing. `os.scandir` raises `FileNotFoundError` for a link whose target is gone, and that error is mapped to "no user files". Reproduced: `~/.config/autobook/normaliser` → a dotfiles checkout that has moved or isn't mounted. `load(link).version` was `1-d7b5c9384833`, the same as `load(<absent dir>).version`. It also contradicts the patch's own rule that a broken *profile* link raises (`tests/test_normaliser.py:325-333`). Fix: when `FileNotFoundError` is raised, return `[]` only if `not os.path.lexists(directory)`; otherwise raise `NormaliserError`. Add a test with a dangling directory symlink.
- NEEDS-HUMAN [impl] — `src/autobook/pipeline/normaliser.py:126-127`: a relative `XDG_CONFIG_HOME` is used as given, so it resolves against the current working directory. The XDG Base Directory spec (the freedesktop.org rules for config paths) says relative values are invalid and must be ignored. Concrete case: with `XDG_CONFIG_HOME=rel`, `_default_user_dir()` returns `rel/autobook/normaliser` (checked). The profiles in effect, and so every token and the `version`, then depend on the directory autobook was started from. Fix: use the variable only when `os.path.isabs(config_home)`; otherwise fall back to `~/.config`. Add one `monkeypatch.setenv` test.
- NEEDS-HUMAN [human] — `src/autobook/pipeline/profiles/sepa.toml:36`: the end of a tag's value is found by looking ahead for the five named tags only. Other real SEPA field tags (`ABWE+`, `KREF+`, `IBAN+`, `BIC+`, `DEBT+`) are not boundaries, so they are swallowed into the previous value. Reproduced: `SVWZ+MIETE EREF+1 ABWE+MUSTER HAUSVERWALTUNG` → `MIETE`. The `EREF+` value runs to the end and takes the payee text with it. And `SVWZ+MIETE ABWE+X` would leave `ABWE+X` in the token. The brief names exactly five tags, so this follows the brief. A human should decide whether "up to the next SEPA tag" should cover the full tag set before #24 builds vectors on these tokens.
- NEEDS-HUMAN [human] — `src/autobook/pipeline/normaliser.py:242-251`: the version digest covers `NORMALISER_VERSION`, the profiles and the mapping. It does not cover the interpreter's Unicode database. `str.upper()` (`:87`) and the regex classes `\d`, `\b`, `\s` all depend on it, and CI supports Python 3.11–3.14 (`.github/workflows/ci.yml:69`), which ship different Unicode versions (this sandbox has 16.0.0). A memo with a character whose case mapping or digit property differs between those versions gives different tokens under the same `version` string. The real-world risk is small. Whether the interpreter or Unicode version belongs in the normaliser version, or in the ch.8 §8.3 tuple, is a scope call.

# Advisory security review: issue 23, normaliser profiles and version

Attacker-reachable inputs this diff touches: statement memo text (threat model "Where untrusted input enters" item 1, controlled by the counterparty). It is the `raw_memo` argument of `Normaliser.normalise` (`src/autobook/pipeline/normaliser.py:83-93`), and the package profiles run on it (`src/autobook/pipeline/profiles/default.toml`, `sepa.toml`). The user directory (`$XDG_CONFIG_HOME/autobook/normaliser/`, profiles and `accounts.toml`) is trusted under the threat model ("the user's own rules file and config in `$XDG_CONFIG_HOME`"). Nothing in this diff is a book write, a review-file path, a model-adapter path or a paperless path.

**No finding at any severity.** What I checked:

- **Resource exhaustion from a memo.** The only non-trivial package pattern is the SEPA tag-and-value rule at `src/autobook/pipeline/profiles/sepa.toml:36`, `(?:EREF|MREF|CRED|ABWA)\+[\s\S]*?(?=…|\Z)`. It is a lazy scan with a fixed-literal lookahead and no nested quantifiers. I ran it with synthetic 100k–200k-character memos (`"EREF+"+"E"*100000`, `"EREF"*50000`, `"EREF+"*20000`, `"CRED+ "+"EREF"*30000`). Each finished in under 5 ms, so the time is linear. The `default` rules (`default.toml:7-26`) are simple anchored literals and digit runs. A user-supplied pathological pattern is self-inflicted, trusted config (the brief says so too). No finding.
- **Counterparty text shaping the token.** The tag rule at `sepa.toml:36` no longer requires a word boundary, so a counterparty can write `ABWA+` (or `CRED+` glued to a word) into the purpose text and delete everything after it. Synthetic case: `ZAHLUNG SVWZ+MIETE ABWA+ BEISPIELMARKT` gives `ZAHLUNG MIETE`. This only removes text that the counterparty already controls. It cannot add text or make an unknown merchant look familiar beyond what writing the familiar name into the memo already does. A wrong token falls through the kNN gates to review. The threat model lists normaliser output quality as lower priority. Not a finding. The no-boundary choice is a deliberate fix from iteration 1, and the glued-tag cases are pinned in `tests/test_normaliser.py:87-90`.
- **Raw memo or personal data leaking.** `NormaliserError` messages include file paths, rule indices and, for a bad account path, `value!r` of the account path (`normaliser.py:237`). They never include memo text. Nothing logs. `NormalisedMemo.raw_memo` returns the memo unchanged to the caller, as the design requires; no model-adapter path exists in this diff. The version string (`normaliser.py:242-251`) is `<int>-<12 hex digits of SHA-256>` over the patterns and the account mapping. Account names enter only the digest, which is not reversible in practice, and the value stays local (staging / version tuple). No finding.
- **Test fixtures.** The SEPA memos in `tests/test_normaliser.py:72-90` are invented. The creditor ID `DE98ZZZ09999999999` uses the synthetic `ZZZ` shape the brief allows. No IBAN-shaped string, no real merchant or person name (`ERFUNDEN PERSON`, `BEISPIELMARKT`, `NEUHEIM KIOSK`).
- **Silent fallback that would hide a user's config.** Iteration 1's finding (an unreadable user directory silently dropped) is fixed: `_user_files` (`normaliser.py:139-153`) maps every `OSError` except `FileNotFoundError` to `NormaliserError`, and a `chmod 0o300` test covers it (`tests/test_normaliser.py:307-314`). Bad TOML, unknown keys, non-string or non-compiling patterns, duplicate or unknown-profile mappings all raise (`normaliser.py:170-226`). This is a correctness property, not an attacker path, because the directory is trusted.
- **Pipeline/book boundary.** The module imports no `gnucash` (`normaliser.py:16-28`) and writes nothing.

The test covers the attacker-reachable cases that matter here: memo tags in all positions, glued tags, and no tag surviving in any token. I found nothing that needs a human decision.
