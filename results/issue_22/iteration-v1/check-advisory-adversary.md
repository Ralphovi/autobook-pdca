# Adversarial review — issue 22 / package-skeleton-contracts-fixtures

I could not re-run pytest here because pytest is not installed in this sandbox. So I judged the red→green proof from `gate-logs/C4-verify.log`, and I tested `autobook.contracts` directly with plain `python3 -I` probes against `$PDCA_TARGET/src`. That is enough for the findings below. None of them depends on the missing toolchain.

## Findings

- NEEDS-HUMAN [impl] — `tests/test_skeleton.py:24-38`: `test_staging_is_a_top_level_block_not_part_of_the_pipeline` can never fail, and the gate log shows it. It is the one test that **passed in the red leg** ("92 of 93 failed": the `.` at position 85 of the red run is this test, the third test in `test_skeleton.py`). `_all_building_blocks()` puts the literal string `"autobook.staging"` into the list at line 25, so the assertion at line 37 checks a value the helper itself added and never imports or looks up `autobook.staging`. The assertion at line 38 is trivially true when `autobook.pipeline` is an empty namespace package (a folder with no `__init__.py`), which is what the reverted tree leaves behind. Today `autobook.staging` is only really covered by the import inside `test_every_block_has_one_entry_point_that_is_not_implemented`. Fix: assert `importlib.util.find_spec("autobook.staging")` is not None, or import it, and use `importlib.util.find_spec("autobook.pipeline.staging") is None` instead of the pkgutil listing.

- NEEDS-HUMAN [impl] — `src/autobook/contracts.py:240-257` and `:302-320`: the serialisers check nothing, and one silent corruption they produce gets **accepted** by the parser. If a `CorpusRow` gets a string path, for example `source_account="Aktiva"`, then `list(row.source_account)` at `:250` writes `["A","k","t","i","v","a"]`. `parse_corpus` accepts that as a valid six-part path (I checked: `ACCEPT str path re-parse`). `mypy --strict` stops typed callers, but the #26 exporter will build rows from values returned by the GnuCash SWIG bindings (the generated Python wrappers), which are typed `Any`. So `source_account=acct.GetName()`, or a full-name string, type-checks and ships a corrupt path. This breaks the brief's invariant that every account crosses the boundary as real path components, and nothing downstream can detect it. The same unchecked writer also emits `amount_cents: 12.5` and `sign: "x"` without complaint. The parser does reject those, so for them the cost is only that the whole corpus fails. Fix: validate on construction (`__post_init__` with the same `_cents`/`_path`/sign checks, rejecting a `str` path), or have `serialise_*` run its output back through `parse_*` before returning it.

- NEEDS-HUMAN [impl] — `src/autobook/contracts.py:286`: coa `type` accepts any non-empty string. `"Equity "`, `"equity"` and `"EQUITYY"` all parse (I checked: `ACCEPT coa free-text type`). The brief (lines 101-102) says the LLM label check will filter placeholder, Equity and Trading accounts "using exactly these fields". A misspelled or differently cased type would then let an Equity or Trading account through as a label candidate. GnuCash's account types are a fixed enum (`NONE, BANK, CASH, CREDIT, ASSET, LIABILITY, STOCK, MUTUAL, CURRENCY, INCOME, EXPENSE, EQUITY, RECEIVABLE, PAYABLE, ROOT, TRADING, CHECKING, SAVINGS, MONEYMRKT, CREDITLINE`), and the brief's rule "a value outside a closed set is rejected" fits it naturally. The brief only gave examples ("e.g."), so this is a gap rather than a violation of the brief's wording. It is still cheap to close now, before #24/#26 start depending on the free-text form. Add a closed set and a test.

- `src/autobook/contracts.py:331-335` (low, informational): `_decode` turns only `ValueError` into `ContractError`. Deeply nested input (`"[" * 100000`) raises `RecursionError` out of `corpus_from_json`, and a non-`str` argument raises `TypeError`. The brief asks for "one module-defined exception type" for rejected documents. Producers are local today, so the risk is small. If touched, add `RecursionError` to the caught types.

## Attempts that did not refute the fix

- **Red→green evidence.** Every red failure is `ModuleNotFoundError: autobook.contracts` (or the pipeline/book equivalent) raised inside the test body, recorded as RAN and FAILED, with 0 collection errors. So the red leg only shows the code exists. That is what the brief planned for a greenfield cycle. The validation behaviour is shown only by the green leg. I checked that the green leg can't pass for the wrong reason: the base documents are proven valid by the round-trip tests (`tests/test_contracts.py:103-148`), each negative test changes exactly one field, and each one expects `ContractError` specifically, not a bare `Exception`. So a rejection can't come from some unrelated field.
- **Integer money (criterion c).** `12.5`, `1250.0`, `True`, `NaN` from JSON, an `int` subclass, `0` and negatives are all rejected for `amount_cents` and `fraction` (`contracts.py:159-165`, `type(...) is int`). Version `1.0`, `True`, `"1"` and an `int` subclass are rejected at `:146`.
- **Dates.** `20260102`, `2026-W01-5`, full-width digits, `2026-02-30` and `0000-01-02` are rejected (`:180-188`). Round-trip of `date.isoformat()` stays 4-digit.
- **Fixtures.** `coa.json` matches `tests/book/synthetic_book.py:14-23` (same 8 paths, types and order). The builder uses a local `random.Random(seed)` (`corpus_builder.py:71`), and the novel row alone owns day 28 of the final month (`:47-50`, `:97`), so it is the only row on the latest date.
- **`.gitignore`.** `*.pdf` lands at `.gitignore:42`, inside the financial-data block and above the synthetic un-ignore lines, as the brief required.
- **Fraction not pinned to 100 in `coa`** (rubric, Money class). This is not a defect of this diff. `coa` describes the tree, and AGENTS.md:116-118 puts the "fraction is 100" check where `GncNumeric(cents, 100)` is built (applier/exporter, #26 and later).
