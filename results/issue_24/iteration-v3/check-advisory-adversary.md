**Evidence holds.** I re-ran `tests/test_knn.py` and `tests/test_skeleton.py` on the patched target with the instance `.venv` (scikit-learn 1.9.1): 43 passed. The frozen red leg (`gate-logs/C4-verify.log:923-962`) shows all 37 kNN tests failing with `AttributeError` inside the test body, and the 6 passes are the skeleton tests. The tests call the real module (`tests/test_knn.py:22`), not a copy. `nox -s gate` is green (`gate-logs/C4-ci.log:66-73`), so the round-1 numpy/mypy fault is fixed. The round-2 findings are also closed: field types are checked exactly (`classifier.py:80-101`), and distances under `1e-9` are snapped to 0 (`classifier.py:211-220`).

I could still break three things:

- NEEDS-HUMAN [impl] — `src/autobook/pipeline/classifier.py:197-208` and `:328`, `:343-345`: **recency weighting is applied only after the k=15 cut, and when distances tie, the cut keeps rows by input position.** So a recent change of habit is invisible for any merchant with more than 15 identical-token rows, and the answer depends on row order. Concrete case: 20 rows `MUSTER VERMIETER` → Lebensmittel dated 1500–2070 days ago, plus 5 rows → Miete dated 10–130 days ago, all with the same source and sign. In old-first order, `query` returns **Lebensmittel, accepted, margin 1.0**. In new-first order, the same rows give Miete (margin 0.566). With decay over all 25 rows, Miete wins 4.58 to 2.14. Old-first is the production order: `build_corpus` sorts by `post_date` (`tests/fixtures/synthetic/corpus_builder.py:100`), `index_rows` keeps that order, and a real book export is chronological too. The result is a confident wrong booking (rubric: *Abstention erosion*) on exactly the recurring payees (rent, salary, subscriptions) where recency should matter most. The brief does not say how to break distance ties when choosing the k neighbours, so this is fixable within scope: ask for every neighbour tied with the k-th distance, sort by `(distance, -post_date)`, then cut to k. Add a test with more than 15 tied rows in chronological order. Criterion (h) uses 5 rows, fewer than k, so it cannot catch this. If the maintainer prefers to leave this to the #25 backtest, the docs should at least say the vote does not weigh recency until after the k cut.
- NEEDS-HUMAN [impl] — `src/autobook/pipeline/classifier.py:173`: **`index_rows` hard-codes `provenance="observed"` and ignores `row.provenance`, so a synthetic corpus row is relabelled and gets through both checks.** Concrete case: `object.__setattr__(build_corpus(0).rows[0], "provenance", "synthetic")` (the same bypass criterion (d) tests on `IndexRow`), then `index_rows(corpus, norm)` → the row comes out `observed`, and `KnnIndex.build` accepts all 115 rows. `index_rows` is the only producer of `IndexRow`s in production, and ch.8 §8.3 now says "there is no path by which a synthetic row can enter". The fix is one line: `provenance=row.provenance`, so the `IndexRow` check sees the real value. Today corpus rows are always `observed`, so the brief's "one observed row per corpus row" still holds. Add a test that smuggles the value through a `CorpusRow`. Low severity, because it needs deliberate tampering. But it is the same class of bypass the patch spent two rounds closing on `IndexRow`, here on the production path.
- NEEDS-HUMAN [impl] — `tests/test_knn.py:412-421`: **`test_exclude_keeps_k_neighbours_when_the_partition_is_larger` does not test what its name says.** All 20 rows vote for one account, so the result is accepted whether 14 or 15 neighbours vote. I changed `classifier.py:328` from `_K + 1 if exclude is not None else _K` to `_K` in a scratch copy, and the whole file still passed (38 passed). The k+1 rule is the part of `exclude` that #25's leave-one-out numbers rely on, and nothing pins it. One fix: build 16 rows (15 → A, 1 → B, with B the farthest neighbour, e.g. a longer token), exclude one A row, and assert that B is among the voters (margin `(14-w_B)/(14+w_B)`, not 1). Another: assert on the share arithmetic directly.
- Not raised (deliberate misuse of a private name; declinable under the rubric's "do not chase silence"): `KnnIndex.__init__` (`classifier.py:232`) is public and accepts a ready-made `partitions` dict with no checks. `KnnIndex({key: classifier._Partition([smuggled])}, "v", 0.5, 0.5, 548.0)` skips both provenance checks. That needs the private `_Partition`, so I am noting it rather than flagging it.
- Not raised (design, not this diff): `char_wb` lowercases and builds n-grams per word, so `"muster miete"` matches `"MIETE MUSTER"` at distance 0. The brief prescribes this vectoriser. A query with no known n-grams returns `candidate` = the smallest path with `share=0.0`. Both gates fail, so nothing is accepted, but a review file would show a candidate that got no votes.
- T2 (`gate-logs/T2-threat-model.log`): left to sign-off, as the brief expected. The patch adds no network access and no new input.
