# Adversarial review: issue 24, knn-index-abstention-gates

I tried to refute the red→green proof, the distance and `exclude` rules, and the docs. The core fix holds. I found one test gap the builder can close, one docs claim that is false under `exclude`, and one design consequence for #25 that a human should see. scikit-learn is not installed in this sandbox, so I checked the numbers with a pure-Python copy of the TF-IDF maths (TF-IDF: term frequency–inverse document frequency weighting). That copy reproduces the brief's Plan values exactly: 0.2368 and 0.3589 for (k), and 0.1056 / 0.2368 for (m). The values quoted below come from the same copy.

## Findings

- NEEDS-HUMAN [impl] — The `df - 1` leave-one-out rule at `src/autobook/pipeline/classifier.py:267-268` is pinned only where df goes from 1 to 0, so a wrong rule passes the whole suite. In (m) (`tests/test_knn.py:561`) every n-gram of the excluded row has df 1. In the 0.9430 case (`tests/test_knn.py:413`) every query n-gram has the same df (16), so any uniform change to df leaves the query vector proportional and the margin unchanged. I checked four variants, and all give 0.943 there: `df - 1`, `df = 0`, df unchanged, and n unchanged. A mutant that sets `df = 0` for every n-gram of the excluded row survives (i) and (m), but it treats n-grams shared with other rows as unseen, which pushes leave-one-out distances up for known merchants. Concrete case that tells them apart: rows `[BEISPIELMARKT, BEISPIELMARKT, BEISPIEL GMBH]` (one partition, same date), query `BEISPIELMARKT` with `exclude=` the first row. The correct rule gives `nearest_distance ≈ 0.000877` and 0.6602 to the GMBH row. The `df = 0` mutant gives 0.00781 and 0.5856. Add that case (confirm the values on scikit-learn first) so the shared-n-gram path of the rule is pinned.

- NEEDS-HUMAN [impl] — The docs claim at `docs/design/architecture/05-building-block-view.md:366-367` ("so an exact token match passes even `max_distance = 0`") is false under `exclude`. With `exclude`, the query's idf uses `n - 1` and `df - 1`, but the remaining rows keep the idf they were fitted with (`classifier.py:257-274`). Whenever the query's n-grams have different dfs, the two weightings stop being proportional, so an identical remaining row is no longer at distance 0. With the rows above, the surviving exact duplicate measures 0.000877. That is above `_IDENTICAL` (`classifier.py:55`), so `max_distance=0` fails the distance gate on a leave-one-out of a repeated merchant. The sentence needs to say it holds without `exclude` only. The `exclude` bullet at `:390-395` says "exact on the query's side only", but it does not spell out this effect.

- NEEDS-HUMAN [human] — The same mismatch is a bias that #25's calibration will inherit, and the brief undersells it. The brief (*Leave-one-out*, "What stays approximate") presents the leftover error as minor. In practice, under `exclude` every repeated merchant whose n-grams also appear in other memos gets a distance a little above 0 to its own duplicates. In production, a new identical memo measures exactly 0 to them. So leave-one-out distances for known merchants run slightly high compared with production. This is the opposite direction from the novel-merchant bias that (m) fixed. It matters most at very small `max_distance` (0 is allowed and has its own documented meaning). A human should decide whether #25 can live with this (the effect is about 1e-3 in my example, but it grows with how many n-grams the merchant shares) or whether the rule should keep the fitted idf for n-grams that other rows still contain. That alternative would change (m)'s pinned 0.2368, so it is a brief change, not a builder fix.

# Security review: issue 24, kNN index with abstention gates

**Untrusted input this diff touches:** the query `token` passed to `KnnIndex.query`. It is the normalised memo of a statement line (threat model "Where untrusted input enters" #1: counterparty text). ## Findings

- NEEDS-HUMAN [human] — **Low to Medium (abstention erosion; nearest rating: "a gate that lets a low-confidence proposal through as confident")**, `src/autobook/pipeline/classifier.py:269` (`_Partition._distances`, query weight `(1 + ln count) * idf`), with `sublinear_tf=True` at `:205`. **Input:** memo text. **Who controls it:** any counterparty, or a bank's memo format by accident. **What goes wrong:** unseen n-grams (character fragments) do push the query away from history, as criterion (k) asks. But repeating a *known* merchant name raises the weight of its n-grams by `1 + ln c`, and since those n-grams point in the same direction as the history row, the novel part of the memo gets diluted. A memo for a merchant the user has never booked can then pass the distance gate and get pre-marked `a`. The brief chose sublinear tf on purpose (brief lines 93 and 115), so this is a design question, not a builder slip. Options: use binary query term frequency (each n-gram counts once), dedupe repeated words in the token before the query, or accept the risk and record it in the threat model. Whoever decides should also check whether #25's backtest would ever see memos like this; if not, a threshold fitted on clean history will not catch it. One unit test pins it: the query above with the name repeated 5 times must not be accepted at `max_distance=0.3`.
