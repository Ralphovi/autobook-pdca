# Adversarial review — issue 24 / knn-index-abstention-gates

Bottom line: the red→green proof holds, and I could not break the kNN logic with a concrete input. The patch still does not pass the project gate. The new scikit-learn dependency pulls in numpy, and mypy (the type checker) fails on numpy's type stubs. `check-gates.json` already says `overall: fail` because of this. Any verdict that calls the patch done is wrong until that is fixed.

I had no Python toolchain in this sandbox (no pytest, no scikit-learn), so everything below comes from the frozen gate logs and reading the source at `$PDCA_TARGET`.

## Findings

- NEEDS-HUMAN [impl] — `pyproject.toml:31` + `pyproject.toml:101-104` (sklearn override): the `C4-ci` gate fails on both attempts, in the `types` session: `numpy/__init__.pyi:737: error: Type statement is only supported in Python 3.12 and greater [syntax]` (gate-logs/C4-ci.log:36 and :108). Cause: `dependencies = ["scikit-learn>=1.5"]` installs numpy into the mypy environment. mypy is set to `python_version = "3.11"` (`pyproject.toml:89`), so it cannot parse numpy's stubs, which use the 3.12 `type X = ...` syntax. The new override silences only `sklearn.*`. Something in the mypy import graph still reaches numpy. The likely path is pytest's typed `_pytest/python_api.py` importing `numpy.ndarray` under `TYPE_CHECKING`, which `tests/test_knn.py` drags in through `pytest.approx`; I could not confirm this without pytest installed. The failure does not depend on the interpreter, because mypy targets 3.11 everywhere, so the PR's CI `types` job will also be red. Fix: add an override so mypy does not parse numpy (for example `module = ["numpy", "numpy.*"]` with `follow_imports = "skip"`), plus scipy if it shows up next. Then re-run `nox -s gate`. Do not raise `python_version`, because `requires-python` is 3.11.
- NEEDS-HUMAN [impl] — `src/autobook/pipeline/classifier.py:248` (`row._validate()` in `build`): the second provenance check is a method lookup on the row's own class, so a subclass can turn it off. Concrete case: `class R(classifier.IndexRow): def _validate(self) -> None: pass`. Build `R(...)` with `provenance="observed"`, then `object.__setattr__(r, "provenance", "synthetic")`. It passes `isinstance(row, IndexRow)` at `:246`, its `_validate` does nothing, and the synthetic row enters the index. AGENTS.md says synthetic rows "must not be able to enter the index" as a structural rule, and the brief's criterion (d) is about getting around the constructor. The `object.__setattr__` test (`tests/test_knn.py:167`) covers only one way around it. A one-line fix closes the gap: call `IndexRow._validate(row)` instead of the bound method, or require `type(row) is IndexRow`. Add a test for the subclass route. Low severity: it needs deliberate misuse, but the brief makes this refusal an invariant.
- NEEDS-HUMAN [impl] — `tests/test_knn.py:367`: `test_the_result_holds_one_account_and_the_stub_entry_point_remains` is the one bundle test that passes on the red leg (gate-logs/C4-verify.log: 31 of 37 failed; the other 6 green are the 5 skeleton tests plus this one). That is acceptable for a regression guard, but its name claims "the result holds one account" and it asserts nothing about `KnnResult`. The brief's "Single account" invariant (no split type) has no test. Either rename it, or add a check that `KnnResult` has exactly one account-typed field (`account`, a single `tuple[str, ...] | None`) and that the module exports no split type.

## Attempted, could not refute

- **Red→green evidence** (gate-logs/C4-verify.log): the green leg ran 37 and passed 37 after the dependency sync installed scikit-learn. The red leg ran 37 with 0 collection errors and failed 31 on `AttributeError`, meaning the tests really ran against the stub. The tests call the production `classifier` module through the module object. There is no copy or mock of the logic. The split-vote, recency and `exclude` tests each have a "wrong implementation" outcome that a broken fix would hit: margin 1/3 if nothing is excluded, margin 1 if both copies are excluded, and `LEBENSMITTEL` if there is no decay (`test_a_very_long_half_life_restores_the_count` pins the opposite).
- **Out-of-vocabulary query** (`classifier.py:176-190`): a non-blank token with no n-gram in the partition's vocabulary becomes a zero vector. The cosine distance is then 1, which fails the distance gate because `max_distance < 1`. All weights are 0, so the margin is 0 and fails too. It abstains. Partitions holding only blank tokens skip fitting (`:169`) and abstain on distance.
- **`exclude` with more than k+1 rows tied at distance 0** (`classifier.py:293-302`): if the excluded row is not in the k+1 returned, nothing is dropped. The vote then has k neighbours that do not include it anyway, so the leave-one-out result stays correct.
- **Extreme half-life / far-future `as_of`** (`classifier.py:313`): weights underflow to 0, total is 0, margin is 0, so the margin gate fails and it abstains. NaN, inf and values ≤ 0 are refused at `:240`.
- **Float boundaries**: with a single voting account, `top == total`, so the margin is exactly 1.0 and `min_margin=1.0` is accepted (`test_boundary_thresholds_are_accepted`). A tie gives a margin of exactly 0, which can never pass because `min_margin > 0` is enforced at `:238`.
- **Rubric classes in scope** (abstention erosion, privacy): no threshold default is set in code. `KnnError` messages name fields and never tokens or account paths (`test_a_refused_row_message_does_not_carry_the_token`). Neither the tests nor the gates add a synthetic route besides the one noted above.
