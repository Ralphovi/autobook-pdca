# Adversarial review — issue 24 (kNN index with abstention gates)

Both gating checks are green in the frozen logs, and the red→green evidence holds. C4-verify shows 39 passed with the fix and 33 of 39 failed without it (`gate-logs/C4-verify.log`). The red failures are `AttributeError` on the missing names inside test bodies, with no collection errors. The 6 that pass on the red leg are the 5 skeleton tests and `test_the_cascade_entry_point_is_still_the_stub`, which is expected. C4-ci (the full `nox -s gate`: format, lint, mypy, tests, typos, docs) passes, including `types`, after the numpy `follow_imports = "skip"` override. The tests call the production `classifier` module directly, not a copy.

I ran probes against the patched `target/src` using the instance `.venv` (scikit-learn 1.9.1, numpy 2.5.4). They found three new problems in this diff. The first is serious.

- NEEDS-HUMAN [human] — `src/autobook/pipeline/classifier.py:184-190` together with `:301`: **when more than k=15 rows share a token, which neighbours vote depends on the order the rows were passed in, so the tier can accept a stale account with full confidence.** Identical tokens all have the same distance, so `kneighbors` breaks ties by row position. `build_corpus` sorts oldest first (`tests/fixtures/synthetic/corpus_builder.py:100`), and the book export is presumably in the same order. Concrete case: 24 monthly `MUSTER HAUSVERWALTUNG` rows go to `("Ausgaben","Miete alt")`, then 6 recent monthly rows go to `("Ausgaben","Miete neu")`. In chronological order, `query(..., as_of=AS_OF)` returns `account=Miete alt, margin=1.0, failed_gates={}`: accepted, and wrong. None of the 6 recent rows was among the 15 voters. Pass the same rows in reverse order and it abstains (`margin=0.06`, `{"margin"}`). A 30-old/10-recent version gives the same result. This is a confident error on a recurring merchant, the most common real case (the *Abstention erosion* rubric). It also defeats the recency weighting that criterion (h) is meant to pin. The test for (h), `tests/test_knn.py:310`, uses only 5 rows, below k, so it cannot catch this. Possible fixes: order tied distances by `post_date`, newest first; let every row tied with the k-th distance vote; or remove duplicate token/destination rows before voting. Picking one is a semantic choice that #25's backtest will measure, so a human should make it rather than Do. Whichever is chosen, add a test with more than 15 identical-token rows, built in chronological order.

- NEEDS-HUMAN [impl] — `src/autobook/pipeline/classifier.py:115` (and the doc claim at `docs/design/architecture/05-building-block-view.md:373`, "so the check cannot be overridden"): **the provenance check is a `not in` test, which an object with its own equality can pass.** `IndexRow(..., provenance=unittest.mock.ANY, ...)` passes the constructor and `build`, and the query is accepted. The same happens with `class S(str): __eq__ = lambda s, o: True` and `S("synthetic")`: `build` accepts a row whose `provenance` string is `"synthetic"`. The round-1 subclass hole was closed for the row (`type(row) is not IndexRow`, `:250`) but is still open for the field. Fix: in `_check_row`, require `type(row.provenance) is str` before the membership test (and the same for `sign`, `token` and `normaliser_version` if the doc's claim is meant to hold). Add a test with a `str` subclass. This needs deliberate misuse, so severity is low, but the brief makes this refusal an invariant and the docs now claim it cannot be bypassed.

- NEEDS-HUMAN [impl] — `src/autobook/pipeline/classifier.py:190` and `:333`, with `tests/test_knn.py:298`: **an exact token match does not always get distance 0.** The clamp only removes negative values. scikit-learn often returns `2.22e-16` for identical vectors: in 92 of 300 random tokens, an index containing the exact token returned a nonzero `nearest_distance`. In a realistic 30-row partition, `MUSTER HAUSVERWALTUNG` matched itself at `1.11e-16`. Validation allows `max_distance=0.0` (`0 <= max_distance`), and with that setting these exact matches fail the distance gate. `test_boundary_thresholds_are_accepted` passes only because `"BEISPIELMARKT"` alone happens to come out at exactly 0, so the test is luck-dependent and may break on a different numpy or BLAS (the math library numpy uses). Fix: round distances below about `1e-12` to 0, or stop claiming `max_distance=0` as a supported boundary. Low practical impact, because no backtest is likely to pick 0.

- `src/autobook/pipeline/classifier.py:324-339`: when the total weight is 0 (every neighbour at distance 1: no shared n-grams), `candidate` is still set. It is just the alphabetically smaller account with `share=0.0`. For example, the query `"XYZQWV"` against rows `ABCDEF` and `GHIJKL` gives `candidate=("Ausgaben","Lebensmittel")`. The brief does not specify this case, and both gates fail, so nothing is booked. But a review that "shows the candidate" (the brief's reason for the field) would show an account with no support at all. Consider `candidate=None` when the total weight is 0. Minor; not raised as NEEDS-HUMAN.

I also tried these and found no problem: the `exclude` logic (the k+1 fetch, dropping one equal row, the empty-after-exclude path; the tests for (i) would catch both removing two rows and removing none); NaN or infinite thresholds and half-lives (refused); a version mismatch on an empty index (`_normaliser_version is None` accepts any version, but every query on an empty index abstains anyway); cross-partition leakage (the key is an exact `(tuple, sign)` match); and whether the C4-ci pass could hide a mypy skip of project code (the override covers only `numpy`/`numpy.*`, and nothing in `src` imports numpy).

### Advisory — security-review

# Security review — issue 24 / knn-index-abstention-gates

Attacker-reachable inputs this diff touches: **statement memo text** (threat model "Where untrusted input enters" item 1, written by any counterparty). It reaches this code as the normalised `token` on both index rows (`index_rows`) and queries (`KnnIndex.query`). The other inputs here (booking history, provenance, normaliser version, thresholds) are trusted under the threat model: the user's own history or code-side values.

**No finding.** Here is what I checked and why each is clean:

- **Gate bypass from memo text (would be High: "a kNN proposal passes with either gate failed").** `src/autobook/pipeline/classifier.py` `_vote` lists every failed gate and sets `account` only when no gate failed. A memo with no n-grams in the partition's vocabulary turns into a zero vector, so its cosine distance is 1. `build` requires `max_distance < 1`, so that query always fails the distance gate. Empty or all-blank tokens, and empty partitions, return `failed_gates={"distance"}` with no candidate. When the total weight underflows to 0 (very old rows), margin is 0, and `min_margin > 0` rejects it. Ties can never pass because of the same `min_margin > 0` rule.
- **NaN distance.** The clamp `min(1.0, max(0.0, d))` would turn a NaN into 0.0, which passes the distance gate. I checked whether that can happen. It can't with this setup: scikit-learn's brute-force `metric="cosine"` goes through `cosine_distances`, which normalises zero rows safely and clips to [0, 2]. That makes this a hardening note at most, not a finding. I did not run it (no scikit-learn in this sandbox), so this rests on reading the code.
- **One account only (threat model "Only rules produce splits").** `KnnResult.account` is a single `tuple[str, ...] | None`, and the module exports no split type. A new test now pins both (`tests/test_knn.py`, `test_the_result_holds_one_account_path_and_no_split_type_exists`). Checking that account against the live tree belongs to the cascade, which is still a stub here, so it is out of this diff's scope.
- **Synthetic rows entering the index (Medium).** Two places refuse them: `IndexRow.__post_init__` and `build`. `build` requires `type(row) is IndexRow` and calls the module-level `_check_row`, so last round's subclass route is closed. Tests cover the constructor, the `object.__setattr__` bypass and the subclass route. A deliberately hostile `str` subclass assigned with `object.__setattr__` could still fake `in _PROVENANCE`. That needs hostile code running in the same process, not statement data, so it is outside the threat model's attackers. I am not raising it.
- **Personal data in errors/logs.** `KnnError` messages name the field and type, never the token or account path. A test pins this (`test_a_refused_row_message_does_not_carry_the_token`). The module does no logging and makes no network calls.
- **Resource use.** Char n-grams (3–5) make TF-IDF cost grow in step with memo length. Queries are brute-force over one partition, which is in proportion to the user's history and not something a memo can inflate. There is no persistence and no file I/O.
- **Abstention erosion (rubric).** Thresholds have no defaults and are range-checked. Nothing widens a threshold. The partition key `(source_account, sign)` stops one account's history from voting for another.
- **Dependency.** `scikit-learn>=1.5` from PyPI with no upper pin (`pyproject.toml`), as the brief asks. The threat model says nothing about dependency pinning, so this is not a finding. The numpy mypy override only changes type checking, not runtime.
- **T2-threat-model (UNVERIFIABLE, `gate-logs/T2-threat-model.log`).** The patch adds no new input, moves no trust boundary and changes no must-hold property. The threat model already lists the kNN gates and the synthetic-row refusal (`target/.oss-scanner/threat_model.md:166-167`, `:258`, `:269`). In my view no update is needed, but the sign-off owns that call.
