# Security review — issue 25 / rolling-origin-backtest

**Attacker-reachable inputs this diff touches:** one, the memo text inside the `corpus` contract file (threat model input 1, "Statement file contents": memos are counterparty text that ends up in the book history the exporter writes out). The other CLI inputs (`--out`, `--normaliser-dir`, the thresholds) come from the user running the command, so they are trusted. The patch has no book write path, no review file, no model adapter, no paperless code and no network.

**Verdict: no finding.** The one property this patch could break is "nothing personal leaves the machine". I checked it and it holds.

What I checked:

- **Report contents** (`src/autobook/pipeline/trial.py:405-433` in the patched file). Every key is a fixed string or a `YYYY-MM` label built from integer year/month (`_label`, `trial.py:231-232`). Every value is a count, a rate, a threshold the user passed, `HALF_LIFE_DAYS`, or `normaliser.version`. Memo text, tokens and account paths are only used inside `_TokenBayes`, `known` and `_Outcome`, and they never get into the returned dict. `_Outcome` keeps booleans and floats only. A hostile memo has no way into a report key or value, and no per-account breakdown exists. The version is a hash of rule content and account mapping, not names (`src/autobook/pipeline/normaliser.py:350-361`).
- **stderr on refusal** (`trial.py:505-513`). `KnnError` messages are documented as field-only (`src/autobook/pipeline/classifier.py:64-70`). `NormaliserError` messages name profile files and paths from the user's own config dir. `ContractError` messages from `corpus_from_json` (`src/autobook/contracts.py:135,144,286,290`) echo a bad `sign`, `provenance` or date string, but never `raw_memo` or an account path. `OSError`/`UnicodeDecodeError` are reduced to the exception type name. That would be Low at most, it predates this patch, and it is not a memo leak.
- **Crash or hang from a hostile corpus.** `_TokenBayes.classify` (`trial.py:205-224`) works in log space with log-sum-exp, so no word count can overflow `math.exp`. Its inputs are counts ≥ 1 per class, so `math.log` never sees 0. Run time is one index build per month plus one leave-one-out build, roughly linear in rows times months. Nothing grows out of proportion to the input.
- **Threshold injection** (`--max-distance nan`, `inf`, `1.5`). `KnnIndex.build` refuses these up front (`classifier.py:327-334`; `0 <= nan` is false). `backtest` calls it before any month is tested (`trial.py:375`), and the test pins this (`test_thresholds_are_refused_even_when_no_month_is_tested`). `json.dumps(..., allow_nan=False)` stops a non-finite value from being written silently.
- **Synthetic rows reaching the index** (Medium on the scale). Rows go through `index_rows` and `KnnIndex.build`, which recheck `provenance` (`classifier.py:340-343`). The patch does not get around that check.
- **No-future rule and thresholds.** The patch only measures. It writes no threshold, and the sweep re-applies the gate checks to stored results (`trial.py:287-306`) without feeding anything back. Leave-one-out appears only under `upper_bound`. No gate or threshold in the live cascade changes, so the "kNN proposal passes with a gate failed / threshold lowered" class does not apply.
- **Test coverage of the hostile case.** `test_cli_writes_a_report_without_identifying_data` (test file lines 658-702 in the patch) checks that no merchant token or account-path component of `build_corpus(0)` appears in the report text, and that no `2025-01-` day-level date does either. `test_cli_refuses_a_file_that_is_not_a_corpus` checks that no report file is written on refusal. That covers the privacy property this diff is responsible for. Stderr is not asserted, but its contents are bounded by the upstream error classes listed above, not by this patch.

Not security (left for other reviewers): the C4-ci gate fails on its `fmt` and `lint` sessions (`gate-logs/C4-ci.log`). That is a formatting and lint problem, not something an attacker can reach.
